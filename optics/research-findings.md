# Deep-Research Findings: LEGO Technic Afocal Webcam-to-Eyepiece Coupler

## 1. LEGO CAD / instruction-generation tooling on Linux

**Verdict:** The classic LDraw stack is alive and Linux-native, but for a *headless, agent-driven* workflow the strongest path is **OpenSCAD** (fully CLI-drivable, in nixpkgs as `openscad`) using the `cfinke/Technic.scad` library for Technic geometry, with the LDraw route (LeoCAD headless CLI + hand/script-written `.ldr` text) reserved for when you specifically need step-by-step *building instructions* rather than a printable solid.

**Toolchain maintenance + nixpkgs status:**
- **LeoCAD** — actively maintained (leozide/leocad). **IN nixpkgs** as attribute `leocad`, version 21.06. Source: https://github.com/NixOS/nixpkgs/blob/master/pkgs/applications/graphics/leocad/default.nix . Build-failure caveat: nixpkgs issue #371825 (https://github.com/NixOS/nixpkgs/issues/371825) reported leocad failing to build, but the root cause was its `povray` dependency (`propagatedBuildInputs = [ povray ]`), not leocad itself; the issue is closed and the povray fix was submitted as PR #371983. Verify live Hydra build status before relying on it. Also available as Flatpak (https://flathub.org/apps/details/org.leocad.LeoCAD), Snap (`snap install leocad`), and AppImage.
- **LPub3D** — actively maintained by Trevor Sandy (https://trevorsandy.github.io/lpub3d/). **NOT in nixpkgs.** Distributed as AppImage, Snap, and Flatpak (`io.github.trevorsandy.LPub3D`, https://flathub.org/en/apps/io.github.trevorsandy.LPub3D). This is the tool that actually generates polished step-by-step instructions (PLI/BOM, callouts, cover pages).
- **LDView** — maintained (tcobbs/ldview). **NOT in nixpkgs**; available on Flathub as `io.github.tcobbs.LDView` and bundled inside LPub3D as a renderer.
- **LDraw parts library** — **NOT a standalone nixpkgs package.** In nixpkgs it is fetched inline inside the leocad derivation as `complete.zip` and wired via the `LEOCAD_LIB` env var. Download directly from https://ldraw.org/ .

**Scriptable / headless (the key question):**
- **LeoCAD has a real CLI.** Documented flags at https://www.leocad.org/docs/cli.html and the Debian manpage https://manpages.debian.org/testing/leocad/leocad.1.en.html . It renders PNG headlessly and exports without GUI interaction: `--html` (create an HTML instructions page), `--export-csv` (parts list), `--export-wavefront`/`--export-3ds`/`--export-collada`, `--camera`, `--viewpoint`, `--orthographic`, plus image width/height. Example from the manpage renders a `.lcd`/`.ldr` to a PNG and exits. `LEOCAD_LIB` (or `-l`) points to the parts library.
- **LDView** has extensive command-line snapshot options; LPub3D supports console/headless operation ("console commands with headless operations", `-SaveSnapshotsList`) per its release notes.
- **The `.ldr`/`.mpd` format is plain text an agent can emit directly.** This is the single most important fact for the no-GUI agent. Format spec: https://www.ldraw.org/article/218.html . Line type 1 (a part reference) is:
  `1 <colour> x y z a b c d e f g h i <part>.dat`
  where `x y z` is the translation and `a b c d e f g h i` is the top-left 3×3 of a 4×4 homogeneous transform. A model point (u,v,w) maps to (u',v',w') via u' = a·u + b·v + c·w + x, and similarly for v' and w'. Identity orientation is `1 0 0 0 1 0 0 0 1`. Other line types: 0 = comment/meta, 2 = line, 3 = triangle, 4 = quad, 5 = optional line.
- **LDraw units (LDU):** 1 LDU = 0.4 mm (from https://en.wikipedia.org/wiki/LDraw ). Key conversions: stud-to-stud pitch = 20 LDU = 8.0 mm; plate height = 8 LDU = 3.2 mm; brick height = 24 LDU = 9.6 mm; LEGO wall thickness = 4 LDU = 1.6 mm. A 1×1 brick footprint is 20×20 LDU; a full brick is 20×20×24 LDU. An agent emitting `.ldr` must know **Y is the vertical axis and +Y points down.**
- **MPD** (multi-part document, `.mpd`) packs multiple sub-models into one text file using `0 FILE name` delimiters.

**Alternatives:**
- **BrickLink Studio (Stud.io)** — official successor to LEGO Digital Designer, macOS/Windows only, C#/Unity. Runs on Linux **only via Wine** (Lutris install script https://lutris.net/games/bricklink-studio/ ; Arch AUR `bricklink-studio` wrapper https://aur.archlinux.org/packages/bricklink-studio ; Eurobricks how-to https://www.eurobricks.com/forum/forums/topic/192484-how-to-run-bricklink-studio-20-on-linux-using-wine/ ). It is GUI-only and **not meaningfully scriptable** — poor fit for a no-GUI agent. Reads/writes LDraw internally.
- **Bricksmith** — macOS-only, effectively unmaintained; skip on Linux.
- **OpenSCAD LEGO/Technic libraries (the high-value path):**
  - `cfinke/Technic.scad` — https://github.com/cfinke/Technic.scad — an OpenSCAD **Technic** piece generator: pins, axles, axle holes, connector hubs, beams. This is the one that covers Technic geometry (pin holes, axle holes, beam spacing), not just studded bricks.
  - `cfinke/LEGO.scad` — https://github.com/cfinke/LEGO.scad — studded bricks/tiles/slopes with Technic-style holes; single `block()` module.
  - `paulirotta/PELA-blocks` — https://github.com/paulirotta/PELA-blocks — parametric Technic-compatible parts *designed for 3D printing* with printer-calibration tuning (`top_tweak`/`bottom_tweak`/`axle_hole_tweak`). Best-in-class for FDM fit calibration — directly relevant to your Ender 3.
  - `B-AROL-O/OpenSCAD-lego-library` — https://github.com/B-AROL-O/OpenSCAD-lego-library — beams/plates with custom patterns.
  - `openscad/MCAD` ships `lego_compatibility.scad` — https://github.com/openscad/MCAD/blob/master/lego_compatibility.scad .
  - **OpenSCAD is fully CLI-drivable:** `openscad -o out.stl in.scad`; headless PNG via `openscad -o out.png in.scad --camera=...`; inject parameters with `-D 'var=val'`. Docs: https://files.openscad.org/documentation/manual/Using_OpenSCAD_in_a_command_line_environment.html . Headless caveat: STL export works without a display, but **PNG export needs an OpenGL context** — on a headless box run it under `xvfb-run` (issue https://github.com/openscad/openscad/issues/3368 ). In nixpkgs the attribute is `openscad` (also `openscad-unstable`).

**So what:** For this build, have the agent hand-author a printed eyepiece collar + Technic-pin baseplate in OpenSCAD using `cfinke/Technic.scad` (or PELA for calibrated fit) — 100% text-in/STL-out, no GUI. Reserve LeoCAD/LDraw for producing a rendered *instruction booklet* of the pure-LEGO frame; the agent can write that `.ldr` by hand because 1 LDU = 0.4 mm and stud pitch = 8 mm are essentially the only constants it needs.

## 2. LEGO inventory / sorting tools

**Verdict:** For cataloguing a pile from photos, **Brickit** is the best-known consumer tool but is phone-only with **no public API**. For anything scriptable, use the **Rebrickable API** (well-documented, includes a "which sets can I build from my inventory" Build feature) plus its **bulk CSV catalog download**. Note that the reseller-oriented **brick'em** service *does* now advertise a paid recognition API — but it is minifigure-focused, not a general parts-pile solution.

**Photo-recognition tools:**
- **Brickit** (https://brickit.app/ ; iOS https://apps.apple.com/us/app/brickit-app/id1477221636 ; Android https://play.google.com/store/apps/details?id=com.brickit.brickit ) — photograph a spread-out pile; it recognizes individual parts, suggests builds with step-by-step instructions, and highlights where each brick is in your photo. **Phone-only, no public/developer API.** Its companion **Pileometer** (Brickit Inc.) builds a digital inventory and, per its own store listing, will "auto-recognize 1600 different shapes with precision."
- **brick'em** (https://brickem.io/blog/ai-lego-recognition-api ) — an AI scanner aimed at resellers. As of its March 18, 2026 update the page advertises a paid **API with tiers** ("Developer tier starts at 1,000 requests per month"; a "Founder's Pass" at 400 API calls/month, $15 locked; white-label options for enterprise). Its recognition is **minifigure-focused** (matches against a large minifig database with BrickLink pricing) at a stated **94% accuracy on standard minifigures in good lighting** — so it is *not* the right tool for identifying loose Technic beams/pins, and you'd be paying for a minifig use-case you don't have.
- Google Lens is sometimes used ad hoc but is not part-number precise.

**APIs / bulk data:**
- **Rebrickable API** (https://rebrickable.com/api/ ; v3 Swagger https://rebrickable.com/api/v3/swagger/ ) — requires a free API key generated in profile settings. Rate limit, verbatim from the API docs (via https://forum.rebrickable.com/t/how-specifically-do-api-rate-limits-work/164286 ): **"Normal user accounts are allowed to send on average one request/sec, with some small allowance for burst traffic."** Endpoints include per-part lookup, part categories, colors, "sets a part appears in," user part-lists, and MOC alternate-builds. Rebrickable's **Build feature** ("find which LEGO sets you can build from the sets and parts you already own") is exactly the "what's buildable from my inventory" cross-reference. For bulk work, use the **Downloads page** (daily-updated CSV dumps of the whole catalog — parts, sets, colors, inventories) rather than per-part queries. Python client: `rienafairefr/pyrebrickable` (https://github.com/rienafairefr/pyrebrickable ).
- **BrickLink API** — exists (OAuth-based), oriented to store/catalog operations.
- **Brick Owl API** (https://www.brickowl.com/api_docs ) — rate limit per its docs: **"The API is rated limited to 600 requests per minute for most requests, or 100 requests per minute for bulk/batch,"** plus a per-user daily quota; offers daily bulk catalog dumps (`catalog/bulk`).
- LDraw, Rebrickable, and BrickLink part numbers differ; Rebrickable publishes cross-reference tables in its bulk download — the practical way to map an LDraw `.dat` number to a real inventory part.

**So what:** The agent can't "see" your pile, but it *can* script against Rebrickable's bulk CSV to confirm which common Technic parts your printed adapter should target as attachment points (e.g., friction pin `2780`, beams `32316`/`16615`). Use Brickit on a phone once to check you actually own them. Design the coupler around the commonest Technic pins/beams so an unsorted pile almost certainly contains them; do not build around exotic parts.

## 3. Prior art: camera-to-eyepiece coupling, especially in LEGO

**Verdict:** Direct prior art exists and teaches one clear lesson: **rigidity and correct axial spacing beat adjustability**, and the hardest tolerance is **centering on the optical axis**, because a toy eyepiece's exit pupil is only a couple of millimeters wide. The most relevant single project, **BrickScope**, deliberately uses a *printed collar with a tape-shimmed eyepiece fit* rather than trying to hit tolerance with LEGO geometry — and its webcam path removes the camera lens entirely.

**LEGO / hybrid prior art:**
- **BrickScope** by NeuroHacks — https://www.printables.com/model/1057324-brickscope-lego-compatible-working-microscope-and — 3D-printed, LEGO-stud-compatible modules that build a working microscope. Transferable details: eyepiece parts are "sized to accommodate the most common eyepiece sizes" with holes deliberately **slightly oversized, then shimmed with tape wrapped around the eyepiece barrel** for a tight fit; the webcam module is designed around a **Logitech C270 with the lens unscrewed and removed** (i.e., prime-focus, not afocal), attached via the camera's own 3 faceplate screws; a C-mount / Raspberry Pi HQ camera adapter is also offered. Focus is set by the number of LEGO plates/bricks between lens and sensor plus fine focus by threading the objective. Earlier RMS-threaded version: https://www.printables.com/model/128006-brickscope-alpha-version-rms-threaded-8x10-stud-br .
- **"Camera-Microscope Combiner Made With Lego"** (Instructables) — https://www.instructables.com/Make-a-Camera-Microscope-Combiner-With-Lego/ — a direct hobbyist example of LEGO holding a camera to a microscope.
- **Microbehunter "Making a LEGO Microscope"** — https://www.microbehunter.com/making-a-lego-microscope/ — uses film canisters as the optics-to-LEGO adapter (objective-to-eyepiece ~160 mm) and notes that eyepieces with a rim become hard to remove once pushed into a cut plastic collar.
- **IEEE Spectrum LEGO/RPi microscope** — https://spectrum.ieee.org/build-a-sophisticated-microscope-using-lego-3d-printing-arduinos-and-a-raspberry-pi-2650279954 — LEGO used for structure; the author removed the Pi camera lens entirely and built a LEGO housing to shield the exposed sensor (again choosing lens-off over afocal).
- **LEGO telescope MOCs with "camera adapters"** exist on Rebrickable (e.g., MOC-160852 https://rebrickable.com/mocs/MOC-160852/Beregorn/telescope/ ) but these are display models, not functional afocal rigs.

**Non-LEGO afocal/digiscoping mechanical lessons:**
- **Centering on the optical axis is the tightest, most punishing tolerance.** Digiscoping guidance: if the camera lens is "not perfectly centred over the exit pupil, the image becomes uneven, dark around the edges or noticeably distorted. Even fractions of a millimetre can create visible degradation" (https://stealthbirding.co.uk/blogs/birding/digiscoping-for-birdwatching ). A worked example (Leica digiscoping, http://leicabirding.blogspot.com/2009/06/digiscoping-yet-another-review.html ) notes you're lining the camera up on an exit-pupil circle only "~3.3 mm to 1.6 mm wide."
- **Axial spacing should equal the eyepiece's eye relief**, and the camera entrance pupil should sit at the eyepiece exit pupil. Durham's afocal guide (https://astro.dur.ac.uk/~nm/astro/afocal.html ): "the lens aperture should be about the same size as the exit pupil of the eyepiece and be positioned at a distance equal to the eye relief of the eyepiece." Alpine Astro (https://alpineastro.com/blogs/blog/mars-afocal-and-barlow-projection ): "ideally the exit pupil of the eyepiece should coincide with the entrance pupil of the camera lens." For reference, a typical 25 mm Plössl eyepiece has ~18 mm eye relief.
- **Tilt** matters least of the three for vignetting but causes one-sided blur/uneven focus; at these small exit pupils it is usually swamped by the centering problem.
- **Common failure modes:** vignetting (dark ring — the #1 complaint, from undersized exit pupil, too-wide camera FOV, or excess spacing), inability to reach focus, and flare/ghosting from the air gap between lenses. TelescopeAdapters (https://www.telescopeadapters.com/content/2-adapter-faq ) recommends low-power eyepieces, a large eye lens, long eye relief, a non-recessed lens, and spacing "the camera lens and eyepiece lens … very closely together."

**Rigidity vs adjustability:** Consensus is **rigidity wins once aligned**, but you must be able to *set* the alignment first. Every serious guide "highly recommends" a fixed adapter over hand-holding precisely because the exit pupil is so small that any wobble loses the image. BrickScope's oversize-then-shim design is the practical resolution: adjustable *during setup*, then locked rigid.

**So what:** Because LEGO is springy and hard to hold to sub-millimeter centering, do the centering in a *printed* collar concentric to the eyepiece, and let the LEGO/Technic frame provide only the coarse structural bridge and axial-distance staging. Plan a one-time alignment step, then lock it down.

## 4. Microscope eyepiece mechanical standards

**Verdict:** Real microscopes use a few standard barrel outer diameters — **23.2 mm (biological/DIN, most common), 30 mm and 30.5 mm (stereo)** — with a straight slip-in barrel. But a Smithsonian/NSI toy is **almost certainly not to any of these standards**: expect a non-standard diameter and quite possibly a **non-removable eyepiece**, so plan to clamp to the *outside* of the housing rather than slip over a standard barrel. **Nothing eyepiece-dimensional is published for model B24014N specifically.**

**Standards:**
- **23.2 mm** — international DIN/JIS standard barrel OD for compound/biological eyepieces; "fits most common size compound microscopes" (AmScope EP10X23, https://amscope.com/products/ep10x23 ). Some vendors list "23 mm" and "23.2 mm" interchangeably.
- **30 mm and 30.5 mm** — common stereo-microscope eyepiece ODs (OMAX 23.2→30.5 mm adapter, https://www.amazon.com/OMAX-23-2-30-5mm-Eyetube-Adapter-Microscopes/dp/B00FG8A2MM ).
- Also seen: 1.25″ (31.75 mm) and 2″ barrels (shared with astronomy); historic/cheap units at 0.965″ (24.5 mm).
- Mechanically the eyepiece is a **straight cylindrical barrel that drops into the draw tube**; real units may add a shoulder/flange limiting insertion depth and sometimes a retaining set-screw. BoliOptics (https://bolioptics.com/blogs/guides/how-to-measure-your-microscope-eyepiece-for-the-correct-reticle-size ) warns the *outer* barrel diameter is always larger than the internal bore, and that some units have a fixing screw and may be twist/pull removable or effectively fixed.

**Toy / NSI-Smithsonian line:** The Smithsonian-branded microscopes are made by **NSI International (Natural Science Industries)** and sold as the "150x/450x/900x" (or 100x/450x/900x) die-cast kit (e.g., https://www.amazon.com/NSI-150x-450x-900x-Microscope/dp/B01LVXX5NF ; https://www.hobbylinc.com/htm/nsi/nsi11424.htm ). Published specs cover magnification, die-cast body, mirror illumination, and "a lens cover provided for the eyepiece," but **no eyepiece barrel diameter is published anywhere for these units, and nothing specific to model B24014N is published at all.** These are marketed "no glass" toys with plastic optics; the advertised 900x on a toy is empty-magnification marketing. The nearest *measured* comparison points are the real DIN standard (23.2 mm) and Microbehunter's note that a real 10x eyepiece is ~23 mm and won't fit a 19 mm hole. Cheap compound scopes frequently have the eyepiece captive in a molded plastic draw tube.

**So what:** Do not assume 23.2 mm. **Measure the B24014N eyepiece OD with calipers before designing anything**, and design the printed collar to clamp/register on whatever cylindrical surface is actually accessible (eyepiece top rim or draw-tube exterior). A split/tape-shimmed collar like BrickScope's is the robust choice for an unknown, possibly non-round, possibly non-removable toy eyepiece.

## 5. Fixed-focus webcam afocal coupling feasibility

**Verdict:** The **NexiGo N60 is confirmed fixed-focus** (3.6 mm glass lens, 110° FOV, 1/2.7″ 2 MP CMOS). Afocal coupling is *feasible but imperfect*: the camera being fixed at roughly 0.5 m–4 m instead of infinity introduces a small focus error you correct **by racking the microscope's own focus slightly**, not by changing the camera. Its 110° wide FOV is the real enemy — it guarantees heavy vignetting through a tiny toy exit pupil. **Removing the webcam's lens (prime focus / eyepiece projection) is very likely the better path for this specific hardware**, and the ~2× digital zoom helps only by cropping away vignette at the cost of resolution.

**N60 specs (confirmed fixed-focus):**
- NexiGo's support page: "Some models, such as the N60 or N660, are fixed focus, meaning they only have one focal length" (https://www.nexigo.com/pages/support-and-download ). Product page (https://www.nexigo.com/products/n60-1080p-webcam ): **Image sensor 1/2.7″ CMOS 2.0 MP; Video format YUY2/MJPG; Focus Type: Fixed Focus; Field of View: 110°; supports 2× digital zoom via NexiGo software.** Amazon listing (https://www.amazon.com/dp/B088TSR6YJ ), verbatim: **"The 3.6mm glass lens provides a crisp image at fixed distances and is optimized between 19.6 inches to 13 feet"** (≈0.5 m to ≈4 m). Do not confuse with the autofocus N930AF or the different-sensor N60 Pro 4K (Sony STARVIS, 0.25–2.28 m) — separate products.

**Fixed-focus webcams + eyepiece optics:**
- A true afocal system emits **collimated (parallel) light** from the eyepiece, and a camera **focused at infinity** images it sharply (Wikipedia Afocal photography: "the imaging device's eyepiece produces collimated light and with the camera's lens focused at infinity, creating an afocal system," https://en.wikipedia.org/wiki/Afocal_photography ). A webcam fixed at ~0.5–4 m is *not* at infinity, so there is a focus mismatch.
- **The mismatch is small and fully correctable by the microscope, not the camera.** Physically: if the camera is focused at distance *d*, defocus the microscope so its eyepiece emits slightly *converging* light appearing to come from *d* rather than infinity — i.e., rack the microscope focus a hair past the visual-focus point. Because the N60's near limit is already ~0.5 m, the required adjustment is tiny and well within a microscope's focus travel. Net cost: essentially none beyond a focus-knob tweak; you do *not* need to modify the camera to reach focus.
- The dominant problem is instead **pupil matching**: a high-power toy scope's exit pupil is only ~1–3 mm, while the N60's entrance pupil and 110° FOV are far wider than the eyepiece's field, producing a small bright disc in a dark frame (vignetting). Small exit pupils also force high ISO/noise and are unforgiving to centering (https://stealthbirding.co.uk/blogs/birding/digiscoping-for-birdwatching ).

**Rule of thumb:** A fixed-focus webcam gives a usable afocal image only if (a) its lens is fairly *narrow* FOV (telephoto-ish) so it doesn't see far past the eyepiece field, and (b) the exit pupil roughly fills the camera entrance pupil at the eye-relief distance. A **110° wide-angle webcam fails (a) badly** — wide-angle point-and-shoots are the classic digiscoping vignette generators. So the N60 afocal *will* vignette heavily unless you crop.

**Lens removal / prime focus — likely the better path here:**
- Removing the webcam lens and projecting directly onto the sensor is a well-trodden DIY route (Kitware "Web Cam Surgery" https://www.kitware.com/diy-microscopy-web-cam-surgery/ ; Hackteria DIY microscopy https://hackteria.org/wiki/DIY_microscopy ; and BrickScope itself removes the C270 lens). **Tradeoffs:**
  - *Pro:* eliminates the second lens entirely — no exit-pupil/entrance-pupil matching, no afocal focus mismatch, no lens-to-lens flare, generally far less vignetting; the microscope's optics form the image directly on the sensor, often brighter and cleaner.
  - *Con:* you lose afocal convenience and must control magnification/focus by the *distance* from the image-forming optics to the bare sensor (as BrickScope does with plate counts); you expose the fragile sensor to dust; and scale can over-magnify (empty magnification). Amateur-micrography (http://www.amateurmicrography.net/Articles/Webcam/Part02/webcam02.htm ) notes direct projection "avoids over-magnification" in some setups but results vary.
  - For a *toy* scope with a possibly non-removable eyepiece, the cleanest lens-off approach is to remove the **camera** lens and let the toy's eyepiece project onto the bare sensor at the right spacing (eyepiece projection). This sidesteps the N60's bad 110° FOV.

**Does the ~2× digital crop help?** Mixed. The `zoom_absolute` 2× is a **center digital crop**, so it *does* mitigate vignetting by discarding the dark outer ring and keeping the bright central disc — but it throws away resolution (down to a ~960×540 effective region of the 1080p frame) and cannot add detail the optics didn't deliver. Use it as a framing aid, not a quality gain. (The `pan_absolute`/`tilt_absolute` controls doing nothing on your unit is expected — the N60 has no real pan/tilt/optical zoom; those V4L2 controls are exposed but inert.)

**So what:** For the coupler, budget for **two experiments**: (1) afocal with the N60 lens on, relying on the 2× crop to kill vignette and racking the microscope focus to compensate for the non-infinity fixed focus; and (2) lens-off eyepiece-projection, likely to look better on this toy hardware. Either way the coupler's job is identical: hold the sensor/lens **centered on the optical axis** at a **repeatable axial distance**, rigidly — which again argues for a printed collar concentric to the eyepiece plus a Technic frame for coarse staging.

## Recommendations (staged)

**Stage 0 — Measure and de-risk (before any CAD).**
- Caliper the B24014N eyepiece OD and the draw-tube exterior; determine whether the eyepiece is removable. This single measurement decides the entire collar geometry. Benchmark that changes the plan: if OD ≈ 23.2 / 30 / 30.5 mm and removable, an off-the-shelf adapter (e.g., OMAX 23.2→30.5 mm) or a standard printed collar applies; if non-standard/non-removable, commit to an external-clamp split collar.
- On a phone, run Brickit once to confirm your pile contains common Technic pins (`2780`) and multi-hole beams. If not, buy a small Technic pin/beam assortment — cheaper than redesigning around what you have.

**Stage 1 — Toolchain setup (agent-friendly, headless).**
- Install `openscad` from nixpkgs; clone `cfinke/Technic.scad` and `paulirotta/PELA-blocks`. Print a PELA calibration beam first and record `top_tweak`/`bottom_tweak`/`axle_hole_tweak` for your Ender 3 + filament. Benchmark: pins should insert with a light click and beams should hold without splaying.
- Only if you want a printed *instruction booklet* of the LEGO frame: add LeoCAD (nixpkgs `leocad`, verifying the povray-related build is green) or the LPub3D Flatpak, and have the agent emit `.ldr` text directly.

**Stage 2 — Build the coupler.**
- Design a **printed split collar** concentric to the measured eyepiece, with a Technic-pin-hole flange (8 mm hole pitch, 4.8 mm pin bore tuned per your calibration) so it snaps into a LEGO/Technic frame. Do centering in the printed collar; use LEGO only for the structural bridge and to stage axial distance in plate increments (3.2 mm each).
- Prototype the camera end **twice**: (a) N60 lens-on afocal, (b) N60 lens-off eyepiece projection.

**Stage 3 — Optical tuning.**
- Afocal: set camera-to-eyepiece spacing ≈ the eyepiece eye relief; center precisely; apply 2× `zoom_absolute` to crop vignette; rack microscope focus slightly to compensate for the fixed ~0.5 m focus. Benchmark to switch to lens-off: if vignette still eats >~40% of frame after cropping, or the image is unacceptably dim/noisy, remove the camera lens and go prime-focus.
- Lens-off: adjust sensor-to-eyepiece distance in plate steps for focus/magnification; watch for over-magnification (empty magnification) and back off.

## Caveats

- **Nothing is published for microscope B24014N specifically** — no eyepiece diameter, no teardown. All eyepiece dimensions in §4 are from real (non-toy) DIN/stereo standards and must be treated as *inapplicable until you measure*. The single biggest risk to the whole project is assuming a standard barrel that isn't there.
- **Repology/search.nixos.org could not be machine-read** for LPub3D/LDView; those "not in nixpkgs" conclusions rest on absence of any nixpkgs source file plus package-tracker snippets — strong but worth a 30-second browser check. LeoCAD's presence (`leocad` 21.06) and its povray-linked build failure are directly confirmed in the nixpkgs tree and issue tracker; confirm the current Hydra build is green before depending on it.
- **The brick'em API details changed under research** (its page now advertises paid API tiers and states 94% minifig accuracy, superseding older "no API / 98%" claims). Treat brick'em as minifig-only regardless; it does not solve general parts-pile identification.
- **Toy-optics ceiling:** the N60's 110° FOV and the toy's tiny plastic-optic exit pupil mean image quality will be limited no matter how good the mount is. The mount can only preserve what the optics deliver; expect a small, possibly soft field. Manage expectations accordingly, and prefer the lowest-power objective for imaging.
- The afocal focus-compensation reasoning in §5 is sound optics but was derived here rather than quoted from a single source measuring *this* camera; verify empirically during Stage 3.
